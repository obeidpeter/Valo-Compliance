# Bounded operational preparation coverage

This change extends the finite runner's runtime capability from TPL-07 to the exact set TPL-01 through TPL-11. It does not approve inference, publish content, establish live readiness, or change the one shared additional-$30 allocation. The frozen package still covers 108 content identities and the original 80/60/60 evaluation cases; it does not promise that $30 completes them.

## Supported preparation contract

The existing source intake and retained ChatGPT permission route both support the original operational forms TPL-01 through TPL-12. TPL-12 remains held because its recorded-balance formula has no implemented exact arithmetic validator. TPL-13 through TPL-40, GUD-01 through GUD-30, the 38 named guide/industry sections, and the evaluation lanes remain outside this runner's executable preparation capability. Thus 11 of 40 template IDs have a preparation path; 29 template IDs remain outside it.

`--prepare-candidate <TPL-ID> <actual-provider-terms-snapshot-path>` reconstructs the source-bound form, checks the actual retained provider passages, renders the final canonical DOCX/PDF, inspects those bytes, and saves a held candidate with its private evidence. This path performs no AI authoring, review, inference approval, or publication, even when the legacy recorded-authoring environment option is set. Missing or failed evidence remains a hold. The command does write the requested candidate/private artifacts in development; it is not a read-only inventory command.

The readiness loader requires the saved row's exact ID/version/hash, current intake/policy/provenance, applicable retained rights evidence, all existing mechanical checks, and fresh inspection of the actual private final exports matching the retained report. Draft sample exports do not substitute for these final files. TPL-09 now selects its exact intake-manifest lineage despite sharing the older source file path; legacy TPL-07 provenance remains separately hash-checked. TPL-07's reconstruction and version-4 review request remain unchanged. Other supported forms use version-5 wording about optional internal record keeping.

## Exact proposals and admission

`--prepare [existing-approved-package-id]` retains every ready candidate's distinct two-review proposal in `proposals`, and reports each inspected saved candidate's hold. It does not silently overwrite one pair with another. Existing private reports containing one `proposal` remain supported.

`--admit <private-report-artifact-id> <artifact-sha256> [candidate-version-id]` requires the candidate version when the report contains multiple proposals. Admission rechecks the existing owner-approved parent, exact immutable child requests and candidate evidence; all admitted children use the same parent allocation and attempt ceilings. No new parent approval or budget counter is created by these commands. `--execute <admitted-child-id>` still executes only one exact two-role pair.
