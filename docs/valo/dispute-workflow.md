# Durable test dispute workflow

Implementation target: TRD PAY-008, ADM-009 and EDT-010. Customer concerns are tenant-bound support records, never claims that a bank dispute exists. Finance must use a live managed session, active finance assignment and recent MFA. A provider ID is linked only after server-side canonical GET matches the exact chosen order, transaction, NGN amount and test domain.

Receipt upload, structured evidence and merchant decision are separate immutable preparations, followed by separately acknowledged staff dispatch. Purchase receipts are generated from retained verified financial events, never private document text. Finance supplies and acknowledges factual evidence and its source; the application invents no delivery facts. JSONB roundtrips use canonical payload hashing. Attempt count is constrained to one. A process interruption, lost response or pre-send safety rejection consumes the attempt conservatively; it cannot silently return to a send queue. Only unsent preparations can be cancelled and replaced.

The worker reconciles by GET only. An upload/evidence result that cannot be proved remains held for merchant review. A canonical resolution and amount matching a decision produce `reconciled`, distinct from a received provider acknowledgement: the original transmission receipt remains unknown and no bank victory is inferred. Reordered terminal observations do not restore entitlement. Money acceptance requires a verified-success order and the unreserved balance after refunds and other acceptance intents; reversed orders and ambiguous earlier mutations cannot authorize additional compensation.

Execution is disabled by default. The real adapter additionally requires isolated development, a non-deployed test merchant, the existing checkout gate, the dispute execution gate and recovery effects permission. No real merchant calls, credentials, email dispatch or live-payment enabling were performed for this change. The current Paystack API reference documents GET dispute, upload URL, evidence POST and resolution PUT; it does not document idempotency for these mutations. Resolve evidence is optional generally; defending a fraud claim needs acknowledged evidence under the documented workflow. Official reference checked 2026-11-15: https://paystack.com/docs/api/dispute/ (Fetch Dispute; Add Evidence; Get Upload URL; Resolve a Dispute). Actual merchant behavior remains unverified.

## Privacy and retained data

`valo_payment_concerns` and removable `valo_concern_messages` hold customer and finance thread text. The existing bounded support-content erasure phase removes these copies without changing the signed phase order/count. Public metadata remains in immutable `valo_dispute_audit`. Workspace exports include concern text/messages, customer-visible history and minimal canonical dispute status. Staff identities, internal reasons, intent leases, receipt bytes and provider evidence are excluded from that customer download; this is an explicitly scoped export, not complete privacy fulfilment.

`valo_dispute_intents` retains the immutable prepared financial receipt, supplied evidence fields (which may contain names, email, phone or address), source note, factual preview, decision and acknowledgement identifiers. `valo_dispute_workflows` retains canonical financial status. These financial/audit records and processor copies are retained or held for coordinated privacy/financial handling; this change does not invent a retention duration or declare whole-account deletion complete. A recorded workspace tombstone blocks new evidence and money dispatch. No provider deletion is implied.
