# Durable dispute completion

This change converges onto the existing `valo_dispute_actions`, `valo_dispute_information`, `valo_dispute_transitions` and canonical `valo_payment_disputes` records. It preserves native migrations 0025/0026 and saved financial history. Additive 0028 follows actual workspace export migration 0027; it adds holds, expiring dispatch claims, immutable prepared-input enforcement and separate payment concern threads. The superseded parallel workflow tables are not registered or created.

Customer payment concerns remain separate from bank disputes. Their thread text is tenant-bound, versioned, exportable and removable by the existing bounded support-content erasure phase. Customer-consented structured bank evidence remains available through the native selected-dispute flow. Staff see factual fields instead of raw records, independently acknowledge each dispatch, and can set/release an explicit hold. Canonical linking verifies the selected order, transaction, currency and test-domain amount server-side.

Each provider mutation rechecks current finance role, fresh MFA, claim token/expiry, current payment and canonical state, hold, evidence source, erasure tombstone and competing liabilities after asynchronous provider lookup. Reversed payments cannot dispatch additional compensation. A stopped or uncertain attempt never returns to preparation: the worker fences it and may GET canonical state only. `observed` means a matching non-awaiting canonical financial effect, not proof of the original response receipt or a final bank victory. Evidence/upload uncertainty stays reserved when no documented lookup can prove it. Financial history, existing entitlement restrictions and customer drafts are preserved.

Execution stays disabled by default and additionally requires existing development/test-merchant/recovery gates. No real Paystack, live payment, email or other external message was sent. Current official reference checked 2026-11-15: https://paystack.com/docs/api/dispute/ (Fetch Dispute, Add Evidence, Get Upload URL, Resolve a Dispute). The reference does not document mutation idempotency; acceptance and fraud defence have distinct evidence requirements. Actual merchant behavior remains unverified.

Privacy scope remains explicit. Workspace downloads now project dispute action status and dates without staff identity, claim token or internal payload. Customer concern text, its thread and actual consented information are included. Financial evidence/source records, financial audit and processor copies remain retained or held for coordinated handling; this does not invent a retention duration or certify complete account erasure. Historical signed erasure phase15 and literal `done` remain valid with the native appended phase; no historical signature or completed cursor is rewritten.

Validation is registered in normal CI: native actual PDF rendering/readback, PostgreSQL tenant/finance/concurrency/source checks, new authority/hold/reversal races while the actual adapter waits, immutable payloads, customer thread/export boundaries, explicit HTTP confirmation, and an actual dispatch child killed with SIGKILL before durable acknowledgement. Browser tests use the actual native components, generated clients, account state and unsaved-navigation boundaries. Local strict UI typing/bundling and narrow scanner-exception tests passed; full exact-head CI results must be checked before integration. No local native browser pass is claimed.

The scanner exception is limited to two immutable historical fingerprints at `docs/valo/evidence/dispute-actions-development.json:60`, independently verified as the SHA-256 binding of their referenced source file. It does not exclude hashes, evidence directories, other rules or future commits; altered-context and generic-credential canaries must remain detected.
