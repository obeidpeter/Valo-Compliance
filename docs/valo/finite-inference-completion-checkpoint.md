# Finite inference completion checkpoint

This is private development engineering, not an approved budget, completed corpus, publication or production release.

The disabled allocation package in `evidence/finite-allocation-package-disabled.json` was generated from actual repository files. It freezes 70 content IDs from the current intake plus the original 60 editorial, 80 checker and 60 customer-AI case IDs/hashes. The proposed allowance is up to $30 in additional new application inference, excluding historical unknown account charges, tax, Agent development, hosting and other projects. The supported executable preparer currently covers only the original TPL-07 operational review pair; its worst-case reservation is $0.7411008. No database-backed exact plan or provider call is claimed by the repository proposal.

One actual owner approval may authorize the finite package. The server can then register immutable exact submanifests inside that package without per-item approval. All children share one fixed allocation row and lane attempt ceilings. Parent expiry/revocation is checked before each dispatch, including already-reserved siblings. The approval explicitly replaces the legacy six-per-day publication scheduling throttle for listed finite work; it does not reset history or grant production/customer launch permission. An existing approved package can be selected when preparing a refreshed child; the new prompt timestamp does not create a new parent approval requirement.

Actual dispatch uses lazy runtime initialization, durable authority, full-context reservation, at most two concurrent or unknown attempts, no SDK retries and exact returned model/usage validation. Invalid receipts are not returned downstream. An unknown-priced model suspends further admission. Valid usage is still accounted when approval expires or is revoked during an admitted call. Customer schema retry requires its own explicitly listed key and reservation; an unknown completion cannot retry or cycle batch IDs. Operational roles have separate contexts and are reserved together immediately before the first dispatch, after caller preflight. Exact legacy attempt IDs and cached settled provider receipts can be reused to recover an interrupted artifact write without inventing another call.

Historical reconciliation is read-only preparation. It reads actual private artifact bytes, verifies their hashes and models/usage, and proposes unique candidate/role/request joins with old-entry/source/artifact hashes. Ambiguous, conflicting or missing evidence stays unresolved. It does not mark any prior liability free, mutate history, or misrepresent token estimates as invoices.

Validation recorded locally: 66 test records passed across budget, package, manifest, history, customer domain and actual managed-entry tests. The entry test executes the actual managed adapter, dispatcher, real corpus/source checker and customer organizer with only a controlled ledger adapter/SDK. It includes a cold disabled request with no database/SDK configuration. PostgreSQL concurrency/settlement/delegation tests are extended and require exact-head CI. Native Replit plan preparation, full build and full release evaluation remain pending. No paid inference, account credential, production migration, email or payment was used.

Development commands are registered in the API package. `finite-inference-run.ts --prepare` prepares a new disabled package and a currently eligible exact plan, if any. `--prepare <existing-package-id>` refreshes an exact child under that already-approved immutable package. `--admit <private-report-artifact-id> <sha256>` can register a child only under an actual enabled parent approval. `--execute <batch-id>` rechecks the exact stored plan and current evidence before invoking the real operational review caller. There is deliberately no owner-approval-writing command or HTTP enable switch.
