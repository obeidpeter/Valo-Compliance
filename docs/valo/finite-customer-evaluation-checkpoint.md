# Original customer evaluation preparation

This private development workflow uses the unchanged original `customer-ai.json` corpus: all 60 IDs, case hashes, numeric expectations, full checks and critical failure conditions remain bound. It does not replace those cases with the separate historical `CAI-01..60` fixture suite. The corrected disabled allocation package `3f21b47b43700024af042fa1284ed45503115a1f56dba2bd591d727a68df96a8` and its 108-content/200-case scope are unchanged.

`src/scripts/finite-customer-evaluation.ts --prepare disabled` reads an existing retained synthetic evaluation identity and writes private, disabled proposals. `--prepare <existing-approved-package-id>` reuses the same shared additional allocation. Each exact child binds the current input, original case, corpus bytes, renderer/organizer/preparer code, private plan artifact and explicit second schema-attempt slot. `--admit <private-report-id> <report-hash> <case-id>` admits one exact child only under an already active parent. `--execute <admitted-batch-id>` calls the actual customer draft service, organizer and managed dispatcher; it records actual receipt metadata and distinguishes cached reuse from new outbound attempts. No command enables owner authority or creates a replacement identity.

As written, INV-01, REM-01, REM-03 and REM-06 have complete eligible input. Native actor availability, live safety state, existing exact-request uncertainty, quotas, parent authority and budget still determine readiness. No native prepared pair, real provider run or full original-corpus acceptance is claimed by this code checkpoint. The four cases would offer eight conditional attempt slots; that is not a claim that every retry occurs or that $30 completes all content and evaluations.

Missing metadata is an explicit clarification workflow. An optional final preparation argument names a private JSON file with `kind: "synthetic-customer60-followups"`, `synthetic: true` and `values` keyed by original case ID. Only absent document number, issue/as-of date and due date may be supplied. The original as-written missing-input observation is retained independently. Supplied facts cannot be overwritten, and the original rubric is not weakened. Known semantic conflicts, unsupported inputs and invalid schemas remain held until their genuine application/source contracts are resolved.

Reminder wording is deterministic: supplied future due dates produce upcoming-payment wording, and reminders request payment details for reconciliation if payment was already made. Names, figures, references, dates and recorded balances remain outside the model. The model only selects approved structure and connective text. The prompt version advances to invalidate old cached semantics.

`--controls <explicit-followup-file>` exercises the six original provider fault cases using the actual organizer with controlled responses/errors and no network transport. These reports contain no provider receipts, allocation usage or quality acceptance. Invalid schema, unsafe markup, single schema recovery, timeout-signal routing, rate-limit routing and outage routing are measured separately. An injected timeout error does not prove elapsed SDK timeout enforcement. Real PostgreSQL tests additionally exercise quota, workspace pause, tenant access/context and concurrent manual saving during outage, including an authorised JSON data download. Those tests isolate the financial-context predicate, never create active approval rows, and fail if default SDK dispatch occurs.

Focused checks cover exact corpus/input/code binding, clarification separation, retry slots, disabled/deployed entry, actual customer service and default organizer/dispatcher with controlled storage/ledger/SDK, unchanged frozen proposal hashes, all 45 numeric expectations and six controlled fault routes.
