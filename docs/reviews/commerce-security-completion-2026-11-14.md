## R1 commerce scope and provider facts

The received specification, `lib/valo-core/src/specification.generated.ts`, requires PAY-001–009: server-priced orders, hosted checkout, authoritative confirmation, durable webhooks, atomic fulfilment, recoverable statuses, daily reconciliation, refunds/disputes and receipts. PAY-010 explicitly excludes recurring subscriptions, wallets, split settlements and provider collections from R1. Do not add them to complete this task.

Current official source facts, checked on the review date:

- [Authentication — Test and live modes](https://paystack.com/docs/api/authentication/): separate keys/environments; test transactions do not move money. Test mode has feature limitations and no settlements. Keep secret keys server-side.
- [Transactions — Initialize/Verify](https://paystack.com/docs/api/transaction/) and [Verify payments](https://paystack.com/docs/payments/verify-payments/): initialize on the backend with currency subunits and a unique reference; verification is server-to-server. `data.status`, not the outer API success flag, is the transaction state. A `plan` parameter overrides `amount`, so the R1 adapter must not accept it.
- [Webhooks — Verify event origin](https://paystack.com/docs/payments/webhooks/): current `Paystack-Signature` uses the full `whsec_` secret and SHA-512 HMAC over timestamp, a period and exact raw bytes. Allow 300 seconds of clock skew, validate signature length and compare in constant time; accept a valid rotation signature among multiple `v1` entries. Legacy `x-paystack-signature` uses the API secret and raw-body HMAC without a timestamp until the integration receives the new scheme. Retried events get newly signed timestamps; test retries run hourly for ten hours. Register the raw-body route before JSON parsing. The account's actual active mode still needs checking.
- [Refunds — References/status](https://paystack.com/docs/payments/refunds/): caller references support safe retries; duplicates return 409 and should be looked up, not recreated. References are case-insensitive, 8–64 characters, letters/digits/underscore/hyphen, unique per environment. Pending/processing/needs-attention are not completed refunds; `processed` is distinct from the customer's eventual bank-credit timing.
- [Test payments](https://paystack.com/docs/payments/test-payments/) supplies supported success, decline and refund-scenario fixtures. Use those through hosted checkout; do not store card fields in Valo or evidence logs.

## Download and licence boundary cases

DOC-005/006/007 and EDT-010 distinguish paid master access from customer-owned saved drafts. Build immutable grants bound to workspace, product/version, order and licence terms; do not substitute a generic signed-in check or current catalogue visibility for entitlement.

Test: anonymous, other tenant, unpaid, pending, revoked membership, wrong version, withdrawn master, expired licence and refunded grant; each denies the applicable new master action. Recheck authorization at actual delivery, including signed-link expiry if introduced. No public object URL or predictable object key may bypass the route. Preserve current private/no-store response behavior, integrity checks and private-storage negative tests.

After withdrawal, block unsafe masters from new use and show remediation; retain purchased-version provenance and the customer's saved revisions. An update must not silently rewrite a document. Existing exports and future reuse must follow a disclosed versioned policy. For implementation fixtures, use an explicit proposed policy: refunds stop future master grants, preserve saved drafts and retain draft export access. This is a test policy awaiting commercial acceptance before sales, not a new universal licence rule.

## Production recovery: prove the missing capability

[Replit data recovery](https://docs.replit.com/features/data-and-storage/data-recovery) documents seven-day default production PITR, optional daily backups and up to 28 days on eligible plans; inactive archived databases can skip daily snapshots. Development rollback and production recovery are separate. [App Storage](https://docs.replit.com/features/data-and-storage/object-storage) is project-scoped and does not provide object lifecycle/versioning/retention policies. These source facts neither establish this account's configuration nor a coordinated database/object backup.

NFR-005 requires database RPO ≤1 hour, core-service RTO ≤4 hours and regenerable-export RPO ≤24 hours. The proposed 35-day retention exceeds the documented native maximum. Prepare the target-specific supported recovery procedure, inventory and assertions now; do not invent a retention guarantee, create shadow backup tables or add an in-app dump/restore endpoint.

In an approved isolated target, restore a retained synthetic checkpoint and matching object set; record wall-clock start, restored data cutoff and service-ready time. Verify document hashes/revisions, tenant permissions, current revocations/deletion tombstones, private object denial, missing-export regeneration and publication evidence. Replay payment inbox/reconciliation without duplicate grants or receipts; suppress outbound charge/refund/email side effects in the drill. Prove the deployed worker can reach DB/private storage with intended grants and renderer resources, then exercise interrupted jobs and orphan cleanup. A development crash test or production build is not this drill.
